# ADR-0001 — Day-0 platform decisions

## Контекст

Проект приводится к AMS Realty Platform Core Standard 2.0. Старая схема не содержит business data и не является основой для будущего production schema.

## Решение

| Decision | Value |
|---|---|
| Schema owner | Payload CMS only |
| Database adapter | `@payloadcms/db-postgres` |
| Application IDs | PostgreSQL UUID |
| Localization | Disabled |
| GraphQL | Disabled globally |
| Default relation depth | `0` |
| Maximum relation depth | `3` |
| Blocks storage | PostgreSQL `blocksAsJSON` |
| Version/drafts | Only editorial collections and explicitly approved globals |
| Import-heavy collection versions | Disabled |
| Soft delete | Payload trash for business collections, introduced with their Wave 2 schema |
| Document locks | Payload native locking |
| Money | Integer minor units |
| Area | Integer cm² |
| Geography | Latitude/longitude; no PostGIS |
| Public data | Custom Public Gateway and DTO/select whitelist |
| Anonymous raw Payload REST | Denied for business collections |
| External HTTP | Central outbound security policy |
| Background work | Payload Jobs Queue and separate supervised worker/scheduler |
| Cache invalidation | Worker calls protected internal Next endpoint; worker never calls Next cache API directly |
| Deployment | Dedicated app server and Timeweb Managed PostgreSQL in one region |
| Database cutover | New empty V2 database, not an in-place rewrite |

## Почему выбрано

UUID avoids public enumeration and makes a future reusable core compatible with isolated client databases. A fresh V2 database is safer than converting the empty legacy schema in-place. Payload remains the only owner of application schema, Admin, access control, Local API and migrations.

## Альтернативы

- Keep numeric identifiers: rejected because Standard 2.0 requires UUID.
- Keep GraphQL for internal use: rejected; REST Admin and Local API gateways cover the current need.
- Convert the existing production schema in place: rejected; the existing business collections are empty and the future schema is fundamentally different.
- Add Prisma/another ORM: rejected by the one-schema-owner invariant.

## Последствия

- All future business IDs are strings in TypeScript.
- Existing numeric-ID code is migrated during Wave 0 before schema-dependent implementation continues.
- Legacy migrations remain historical evidence but are not loaded by the V2 Payload configuration.
- Production cutover requires a provider backup, a new Managed PostgreSQL instance or clean database, V2 migrations and a release smoke test.
- Any change to this ADR after first production V2 release requires a new ADR and migration plan.
