# ADR-001 — Payload как единое CMS/backend-ядро

## Контекст

Проекту нужен foundation для быстрого старта UI-потока, базового контентного кабинета и дальнейшего роста в сторону каталога недвижимости. На этом этапе важно не размножать runtime-слои и не заводить вторую систему авторизации.

## Решение

Использовать единое Next.js-приложение, в котором Payload CMS работает как:

- CMS;
- auth/RBAC слой;
- admin-интерфейс;
- data access layer поверх PostgreSQL.

## Почему выбрано

- официальный scaffold Payload уже поддерживает нужный Next App Router контур;
- один runtime упрощает auth, deployment, migrations и сопровождение;
- Payload Admin закрывает текущую задачу рабочего кабинета без отдельной админки;
- foundation остаётся достаточно простым для быстрого старта 40 страниц UI.

## Альтернативы

- Next.js + отдельный backend: отклонено, потому что усложняет foundation без пользы на текущем этапе;
- Next.js + Prisma + отдельная CMS: отклонено, потому что дробит schema/auth/admin и противоречит целевому контракту;
- Better Auth поверх Payload: отклонено, потому что добавляет второй auth-layer и повышает риск дрейфа.

## Последствия

- Все schema-изменения проходят через Payload collections/globals и migrations.
- Любое серьёзное обновление Next.js или Payload требует повторного admin smoke.
- Публичный UI дальше строится поверх query/view-model слоя, а не прямой привязки компонентов к Payload documents.
